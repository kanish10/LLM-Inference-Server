# LLM Inference Server — Continuous Batching

A from-scratch implementation of continuous (in-flight) batching, the scheduling
algorithm behind vLLM, TGI, and every production LLM serving system built after 2023.

A single-threaded C++ scheduler admits queued requests and frees finished KV-cache
slots at every decode step. A Go gRPC gateway fronts it with admission control,
backpressure, and Prometheus metrics.

See `CLAUDE.md` for the full design rationale and specification.

## Architecture

```
Client --gRPC(stream)--> Go Gateway --gRPC(unix socket)--> C++ Engine
                              |                                  |
                         Prometheus                   ContinuousBatchScheduler
                          /metrics                      (single thread, lock-free
                                                          hot path)
```

## Prerequisites

- CMake >= 3.16, a C++17 compiler
- `protobuf-compiler`, `libprotobuf-dev`, `libgrpc++-dev`, `protobuf-compiler-grpc`
- Go >= 1.21 (the module targets 1.25; with `GOTOOLCHAIN=auto`, the default,
  an older local `go` transparently downloads the required toolchain)
- `libgtest-dev` (or CMake will fetch GoogleTest automatically)
- Python 3 with `grpcio`, `grpcio-tools`, `numpy`, `matplotlib`, `pandas`

On Ubuntu/Debian:

```bash
sudo apt-get install -y protobuf-compiler libprotobuf-dev protobuf-compiler-grpc \
    libgrpc++-dev libgrpc-dev golang-go libgtest-dev build-essential cmake
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest
export PATH="$PATH:$(go env GOPATH)/bin"
pip install -r benchmark/requirements.txt
```

## Build

```bash
make proto      # generate Go + C++ protobuf/gRPC stubs
make engine      # build the C++ engine (cpp-engine/build/engine)
make gateway      # build the Go gateway (bin/gateway)
```

## Test

```bash
make test        # C++ unit tests (ctest) + Go tests
```

## Run

```bash
# Terminal 1: C++ engine (mock generator — no model download needed)
./cpp-engine/build/engine --mode mock --listen unix:///tmp/inference-engine.sock

# Terminal 2: Go gateway
./bin/gateway --engine unix:///tmp/inference-engine.sock --listen :50051 --metrics :9090

# Terminal 3: send a request
grpcurl -plaintext -d '{"prompt": "hello", "max_tokens": 16}' \
    localhost:50051 gateway.InferenceService/Generate
```

Prometheus metrics are served at `http://localhost:9090/metrics`.

## Benchmark: continuous vs. static batching

Two experiments, both driving the scheduler in continuous mode
(`evict_finished`) and static mode (`--static`, which waits for the whole
batch to finish before evicting anyone — see "Static Batching Baseline" in
CLAUDE.md) with identical Poisson-arrival traffic and output lengths sampled
uniformly from [16, 512] tokens. Measured on the dev machine this was built
on (500 requests/run, `--batch-size 8 --mock-latency-us 100
--mock-fixed-overhead-us 2000`; re-run `make bench` / `make bench-capacity`
to reproduce on yours):

```bash
make bench             # same offered load for both modes (2.4 req/s)
```

| | continuous | static |
|---|---|---|
| throughput | 637 tok/s | 637 tok/s |
| TTFT p99 | 8.9 ms | 751.2 ms |
| latency p99 | 1258.7 ms | 1474.8 ms |

At a shared arrival rate comfortably under both systems' capacity, neither
is queue-bound, so aggregate throughput ties — the visible cost of static
batching here is **head-of-line blocking**: a new request can't be admitted
until the entire batch (including whatever long-running straggler is still
in it) finishes, so tail latency degrades sharply even though the system
"keeps up" in aggregate.

```bash
make bench-capacity    # static driven at its capacity ceiling; continuous
                        # driven until its p99 matches static's p99
```

| | continuous (6 req/s) | static (2.8 req/s) |
|---|---|---|
| throughput | 1581.2 tok/s | 742.6 tok/s |
| latency p99 | 1688.1 ms | 1673.8 ms |

**2.13x throughput at matched p99 latency** — this is the resume number.
Static's sustainable capacity collapses sharply above ~3 req/s at these mock
settings (queueing runs away, unbounded); continuous stays healthy well
past 10 req/s. `benchmark_results.png` and `summary.txt` are regenerated by
whichever target ran last.

**Why the mock's fixed_overhead matters.** `MockTokenGenerator::forward()`
sleeps `fixed_overhead + latency_per_token * batch_size`. With
`fixed_overhead = 0` (the constructor default, kept for scheduler-test
determinism), per-step cost is exactly proportional to how many sequences
are actively decoding — so an underfull static batch (six slots occupied by
finished-but-unevicted sequences) costs exactly as much per active sequence
as a full one, and the aggregate throughput gap disappears entirely (this
was the first thing measured, and it produced a 1.00x ratio with identical
5311/5312 tok/s — a bug, not a result). Real batched inference isn't like
that: reading model weights from memory is a large per-step cost
independent of batch size, amortized over however many sequences are
actually in the batch. Both bench targets pass
`--mock-fixed-overhead-us 2000 --mock-latency-us 100` to reproduce that.
Override `MOCK_LATENCY_US`, `MOCK_FIXED_OVERHEAD_US`, `BATCH_SIZE`,
`ARRIVAL_RATE`, `STATIC_ARRIVAL_RATE`, `CONTINUOUS_ARRIVAL_RATE`, or
`BENCH_REQUESTS` as `make` variables to re-tune for a different machine —
the sustainable arrival rates are specific to these settings and will shift
if you change them.

## Real model inference (optional)

Polish on top of the core scheduler — the resume claims are about the
scheduling algorithm, which the mock generator already exercises fully — but
verified working end-to-end:

```bash
# Download TinyLlama (~669 MB; models/*.gguf is gitignored)
curl -L -o models/tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf \
    "https://huggingface.co/TheBloke/TinyLlama-1.1B-Chat-v1.0-GGUF/resolve/main/tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf"

# Build with llama.cpp support (fetched automatically by CMake — first
# configure clones it, first build compiles it; both take a while)
cmake -S cpp-engine -B cpp-engine/build-llama -DCMAKE_BUILD_TYPE=Release -DWITH_LLAMA=ON
cmake --build cpp-engine/build-llama -j"$(nproc)"

./cpp-engine/build-llama/engine --mode llama \
    --model models/tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf \
    --batch-size 8 --listen unix:///tmp/inference-engine.sock
```

Point the Go gateway at it exactly as with the mock engine. Sample output
(temperature 0, greedy) confirming both real generation and correct KV-cache
isolation across sequences sharing the same batch slots:

```
PROMPT: "The capital of France is"
OUTPUT: " Paris.\n\n2. B.C. The capital of ancient Rome was Rome.\n\n"

PROMPT: "The largest planet in the solar system is"
OUTPUT: " Jupiter. It is also the most massive planet in the solar system,"

PROMPT: "Water is made of hydrogen and"
OUTPUT: " oxygen, which are the most abundant elements"
```

**KV cache reset was the real gap here.** llama.cpp owns its own internal KV
cache, keyed by `llama_seq_id` — and every `Sequence::kv_slot` the scheduler
hands a `TokenGenerator` doubles as that id. The original design never told
the generator when a slot was freed, so a real model reusing an evicted slot
would silently inherit a previous, unrelated conversation's KV state.
`TokenGenerator::reset_sequence(kv_slot)` (default no-op, since the mock is
stateless across calls) closes that gap; `LlamaCppGenerator` overrides it
with `llama_memory_seq_rm`, and the scheduler calls it in both eviction
paths right after `KVCacheAllocator::free()`. Verified above by running four
sequential prompts through only 2 batch slots (`--batch-size 2`) and
confirming each output stayed on-topic rather than drifting into the
previous prompt's continuation.

## Docker / Grafana

```bash
cd docker && docker compose up --build
```

Builds and runs the engine and gateway containers (sharing a Unix socket over
a named volume), plus Prometheus (scraping the gateway's `/metrics`) and
Grafana (pre-provisioned with a Prometheus datasource and the dashboard in
`dashboards/grafana.json`). Grafana is at `http://localhost:3000` (anonymous
viewer access enabled; admin/admin for the admin account), Prometheus at
`http://localhost:9091`, the gateway gRPC port at `localhost:50051`.

## What this is / isn't

This isolates the ~500-line core scheduling algorithm to understand and demonstrate
it deeply. It is not a production inference server (no speculative decoding, no
prefix caching, no tensor parallelism) and not a vLLM replacement.
