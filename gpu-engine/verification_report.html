M6 — continuous vs. static batching

500 requests · output lengths U(16, 512) · batch 8

The first calibration attempt read a flat 1.00× — a load-testing bug, not a finding: the shared arrival rate was set to 80% of static mode's own ceiling, which keeps static comfortably under-loaded too, so its slot-wasting penalty never gets stressed. Recalibrating off continuous's higher ceiling exposed the real gap.

Why not the historical ~3.2×? Real per-step cost here is dominated by fixed per-layer kernel-launch overhead plus the O(seq_len) attention term (see M5) — a flatter, less batch-sensitive cost profile than a synthetic mock generator's latency, which scales purely with batch size. Plausible, not confirmed — no controlled ablation was run to isolate it. The number wasn't chased higher by re-tuning the load further; that's what the honesty rule is for.

M2 — is 58.5% sequence match actually fine?

FP32 logit-margin analysis at each divergence point

Autoregressive greedy decode cascades: one FP16 rounding flip early in a 32-token sequence contaminates every token after it, so a whole-sequence exact-match metric understates the real numerical accuracy. Checking the CPU-FP32 oracle's own logit margin at each divergence point tells the real story — GPT-2's output distribution has frequent razor-thin top-2 ties.

Across all 17 mismatches in the 41-prompt set, 100% land on the CPU oracle's exact rank-2 (16 cases) or rank-3 (1 case) token, on logits around −50 to −100 — sub-0.2% relative gaps. A teacher-forced, non-cascading probe (feeding the true history at every step instead of a possibly-wrong prior guess) puts real per-step agreement at 1,370/1,520 (90.1%). No kernel bug found anywhere in the pipeline.
